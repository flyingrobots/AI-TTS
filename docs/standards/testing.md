# Testing Standards
- The frame
	- 1. Test at the narrowest boundary that is a contract.
	- 2. Assert on outputs, not internals — harvesting universals, enumerating existentials.
	- 3. One test per behaviour, not one per function — and every diff declares which of the four kinds of change it is.
	- 4. Every assertion must be shown able to fail.
	- 5. For "nothing changed" claims, use generated evidence — not more examples.
	- 6. Every assertion names its oracle.
	- 7. Determinism is constructed, not assumed.
	- 8. Hermetic by default: the test controls everything it observes.
	- 9. Every test carries a size class with enforced resource ceilings, and every suite has a latency budget.
	- 10. Flakiness has a policy: out of the gate the same day, with an owner and an expiry, and never retried into green.
	- 11. Coverage is an inspection instrument, never an objective.
	- 12. Every bug fix ships with a test observed red on the unfixed code.
	- 13. Fuzz what parses; property-test what transforms; keep the corpus as a permanent asset.
	- 14. Concurrency is tested by exploring interleavings, never by stress-and-pray.
	- 15. Every durability or recovery promise is tested by seeded fault injection.
	- 16. Performance tests are controlled experiments, not timings.
	- 17. Golden files and snapshots live under re-baseline discipline.
	- 18. Test code is production code, with recorded deletion criteria.
	- 19. CI gates on trustworthy signals, and on nothing else.
- Test types, with oracle and failure economy
- Reviewer checklist, ordered by kill rate
- Contested territory, flagged honestly
- The standard, compressed

# Testing Standards

> A language-agnostic standard for tests that outlive the code they verify.
## The frame

A test is an experiment: it manipulates a system under controlled conditions and reads a gauge. A suite is therefore an instrument, and CI is the lab protocol that keeps it honest between readings.

Every test occupies a cell in a two-axis grid, and its strength is roughly the product of its coordinates. The first axis is who supplies the inputs — a human choosing examples, or a machine generating them randomly, coverage-guided, or by simulated schedule. The second is who supplies the expectation, which is to say what the oracle is: an exact value, a stated property, a reference implementation, a formal consistency model, or merely "the process did not crash." An example checked against an exact value explores one point with a strong oracle; a crash fuzzer explores billions of points with the weakest oracle available. Differential testing and deterministic simulation are the rare techniques strong on both axes, which is why the projects with the most extreme reliability requirements converge on them: SQLite's SQL Logic Test runs 7.2 million generated queries against SQLite _and_ PostgreSQL, MySQL, SQL Server, and Oracle and demands identical answers ([SQLite testing docs](https://www.sqlite.org/testing.html)), and Jepsen generates concurrent histories under injected faults and checks them against consistency models, finding lost writes, stale reads, and read skew in mature systems whose own suites were green ([Jepsen analyses](https://jepsen.io/analyses); [consistency models](https://jepsen.io/consistency)).

Like every instrument, a suite fails in exactly three ways, and every rule below suppresses one of them. **False confidence**: the gauge reads green while the system is wrong — vacuous assertions, drifted fakes, goldens blessed unread, coverage theatre. This is the worst economy, because the suite is not merely useless; it converts uncertainty into unwarranted certainty. **False alarm**: the gauge reads red while the system is right — brittle interaction tests, structure-mirrored suites, flakes. The cost is not the failed run but the trained response; Google found 84% of its pass-to-fail transitions involved a flaky test ([Where do our flaky tests come from?](https://testing.googleblog.com/2017/04/where-do-our-flaky-tests-come-from.html)), and at that ratio red has stopped meaning anything. **Decay**: readings stay accurate but stop being affordable or believed — the suite slows until nobody runs it, grows until nobody reads it. _Software Engineering at Google_ puts the end state plainly: a bad test suite can be worse than no test suite at all, because tests derive their value from the trust engineers place in them ([ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)).

Hence the meta-rule: **every rule must name the failure it prevents.** A rule that cannot state its failure mode is not a rule; it is a superstition with a lint check. Three sentences hold the rest in one hand — test promises at boundaries, prove every test can fail, control everything a test observes.

## 1. Test at the narrowest boundary that is a contract.

A boundary is a contract when someone outside the change-control of the code depends on it. If nobody outside the module would have to be told about a change, it is not a boundary, and a test pinned to it is a liability.

Ian Cooper's _TDD, Where Did It All Go Wrong_ argues the same point from the architecture side (paraphrased): adopt ports and adapters, and test through the ports; the trigger for a new test is a new behaviour, not a new class or method. He also revives Kent Beck's original meaning of "unit" — the test is the unit of isolation, not the class — which is where the habit of mocking every collaborator came from and why it produces brittle suites ([InfoQ recording](https://www.infoq.com/presentations/tdd-original/); [talk](https://www.youtube.com/watch?v=EZ05e7EMOLM); [Graça's distillation](https://herbertograca.com/2018/08/27/distillation-of-tdd-where-did-it-all-go-wrong/)). _SWE at Google_ supplies the causal reason the public surface matters: tests via public APIs form explicit contracts, so if such a test breaks an existing user will also break — "the most important thing you can do to ensure that your tests fail only in the event of meaningful changes" ([ch. 12](https://abseil.io/resources/swe-book/html/ch12.html)). Tests bound to structure instead earn the name Google's engineers give them: change-detector tests, which fail on any change even when behaviour is unchanged ([ch. 13](https://abseil.io/resources/swe-book/html/ch13.html)).

**In practice.** If the codebase has an explicit boundary — a port, a module API, a CLI, an HTTP surface, a wire format, a durable file — that boundary is the test boundary. Reaching past it to assert on an internal is choosing to depend on the thing the boundary exists to hide. Define the boundary socially, not syntactically, because `pub` is a compiler notion and will be gamed. Two clauses keep the rule from degenerating in either direction. _Narrowest_: read naively, "test through the port" means "test only at the outermost port," which is how a suite becomes a handful of slow end-to-end tests; the boundary you want is the edge of the module that owns the behaviour. _Promote rather than reach_: if you feel the need to test an internal — a B-tree rebalancer, a register allocator, a conflict lattice — that need is a signal the internal wants to be a module with its own narrow API, which turns the suite into an architectural forcing function. Conversely, a helper serving one or two callers should not be frozen by direct tests; doing so converts an implementation detail into a pseudo-contract.

**Prevents.** Mockist brittleness and refactoring deadlock, where every internal move breaks tests and the code ossifies; boundary worship and the resulting ice-cream cone; contract-freeze of non-contracts; the accessor added "for tests" that becomes de facto API.
## 2. Assert on outputs, not internals — harvesting universals, enumerating existentials.

"With state testing, you observe the system itself to see what it looks like after invoking it. With interaction testing, you check that the system took an expected sequence of actions on its collaborators." — _SWE at Google_, ch. 12. The chapter is sharper than the quote: interaction tests check _how_ a system arrived at its result when usually you should care only _what_ the result is, and the canonical counterexample is the test that verifies `database.put("foobar")` and passes even when a bug deletes the record immediately afterwards ([ch. 12](https://abseil.io/resources/swe-book/html/ch12.html)).

An artifact, a return value, an exit code, a rendered page, a refusal message, a row in a table. Prefer the thing a user or a downstream system would actually observe. An output is not only a return value: durable writes, emitted messages, authorization denials, released resources, and the absence of a forbidden effect all count.

A useful sharpening: **harvest rather than enumerate.** When asserting a property over an output — every timestamp is pinned, no field leaks a secret, all ids are well-formed — walk the output and check every match, rather than listing the fields you expect to find. A hand-listed field set is blind to the new field, which is exactly where the next bug arrives.

Harvesting has two blind spots the standard names rather than hides. Absence: you cannot walk what is not there, so the field that _should_ be present is invisible to a harvest predicate — harvest universals, enumerate existentials. And vacuity: a recursive check that every timestamp is pinned passes gloriously on an output containing none. Every harvested assertion therefore reports a **witness count** — "found 37 timestamp fields; all pinned," never "all found timestamps were pinned" — and harvest predicates are deny-by-default, failing on any unrecognized shape, for the same reason firewalls are: a rule matching `/secret|token|password/` fails open on the field named `credential_blob`.

**In practice.** Assert semantic projections: parsed records rather than formatting noise, an unordered set where order is unspecified, required fields rather than whole-object equality, a history accepted by a checker. Interaction assertions are permitted only where the interaction crosses a contract boundary and _is_ the behaviour — exactly-once payment, a published event, an audit row written for another system, a cache that must not be consulted more than N times. That is state testing one boundary removed, not choreography; ban it outright and the standard cannot express "the payment provider is called exactly once," a user-visible promise, but permit it freely and every `verify()` becomes a coupling point. Doubles obey the same logic: real implementations first where they are fast, deterministic, and constructible; then fakes owned by the team that owns the real thing and validated by a contract suite running against both ([ch. 13](https://abseil.io/resources/swe-book/html/ch13.html); [Fowler on contract tests](https://martinfowler.com/bliki/ContractTest.html); [consumer-driven contracts](https://martinfowler.com/articles/consumerDrivenContracts.html); [Pact](https://docs.pact.io/university/introduction/step3)); stubs sparingly, each tied to a visible assertion; mocks last. An unowned, uncontracted fake is a fork of someone else's semantics that diverges silently, and its maintainers are always the last to know.

**Prevents.** Change detectors that fail on refactors and pass on bugs; enumeration blindness to the new leaking field; vacuous universals over empty collections; the drifted fake that manufactures green builds for a broken integration; under-assertion — status 200 with no check on the effect.
## 3. One test per behaviour, not one per function — and every diff declares which of the four kinds of change it is.

"Rather than writing a test for each method, write a test for each behavior." — _SWE at Google_, ch. 12. A method-shaped suite has to change every time methods move. A behaviour-shaped suite only changes when the promises change — which is the ideal: "The ideal test is unchanging: after it's written, it never needs to change unless the requirements of the system under test change" ([ch. 12](https://abseil.io/resources/swe-book/html/ch12.html)).

The same chapter enumerates the four kinds of change and which of them should touch tests: pure refactorings should not, new features should not, bug fixes add a test, and only a deliberate behaviour change edits an existing one. That is a usable review question — which of the four is this, and does the diff match? — and this standard promotes it to a **required declaration** on every PR, checked against the test diff. It costs one line of template and is the cheapest high-signal review question here. When a declared refactoring forces test edits, the chapter's own diagnostic applies: either the change is affecting behaviour, or the tests were not written at an appropriate level of abstraction.

**In practice.** Behaviour is bounded from both sides. Too fine is the method-shaped suite; too coarse is behaviour inflation — the 300-line "behaviour" test with six actors and a sleep. Google's discipline cuts both ways: most unit tests need one "when" and one "then," and needing the word "and" in a name is good evidence you are testing two things ([ch. 12](https://abseil.io/resources/swe-book/html/ch12.html); [Keep Tests Focused](https://testing.googleblog.com/2018/06/testing-on-toilet-keep-tests-focused.html)). One behaviour per test is not one assertion per test; that misreading fragments evidence and duplicates setup, and several assertions are right when they establish one atomic promise — a rejected transfer changes neither balance, nor ledger, nor audit count. Name tests as sentences about behaviour, `transfer_rejected_when_balance_insufficient` rather than `test_process_2`, because the name is the first and often only token in a failure report ([descriptive test names](https://testing.googleblog.com/2014/10/testing-on-toilet-writing-descriptive.html)). For protocol-shaped systems a behaviour may be a short exchange — chapter 12 permits alternating when/then blocks for multistep processes — allowed here, but justified in the commit message rather than treated as the default shape. Note the pairing that makes the rule matter: Beck separates _structure-insensitive_ from _behavioral_ ([Test Desiderata](https://medium.com/@kentbeck_7670/test-desiderata-94150638a4b3)); a suite of tautologies is perfectly structure-insensitive and a snapshot suite is perfectly behavioral, so only the conjunction is worth anything, and Rule 4 enforces the second half.

**Prevents.** Suites rewritten whenever methods move; test edits smuggled into refactorings; behaviour inflation; the table-driven case whose row label cannot identify what broke.
## 4. Every assertion must be shown able to fail.

Break the thing an assertion protects, run it, and require it to go red and to name itself. **An assertion that survives the deletion of its own subject is not a weak test; it is not a test.**

This is mutation testing, and it is not exotic. SQLite runs mutation testing that "verifies every branch makes a difference in output" ([SQLite testing docs](https://www.sqlite.org/testing.html)). Google runs it across the monorepo: Petrović & Ivanković, "State of Mutation Testing at Google" ([ICSE-SEIP 2018](https://research.google/pubs/state-of-mutation-testing-at-google/)), report a system "used by 6,000 engineers in Google on all code changes they author or review, affecting in total more than 13,000 code authors as part of the mandatory code review process"; the follow-up roughly quadruples those figures — 17 million mutants over 760,000 changes, 24,000 developers — while stating that "achieving mutation adequacy is neither practical nor desirable" ([Practical Mutation Testing at Scale, TSE 2021](https://homes.cs.washington.edu/~rjust/publ/practical_mutation_testing_tr_2021.pdf); [DOI](https://dl.acm.org/doi/10.1109/TSE.2021.3107634)). The rule rests on the best-validated proxy for suite effectiveness that exists: Just et al.'s study of 357 real faults found mutant detection correlated with real-fault detection more strongly than statement coverage did ([FSE 2014](https://homes.cs.washington.edu/~rjust/publ/mutants_real_faults_fse_2014.pdf); [DOI](https://dl.acm.org/doi/10.1145/2635868.2635929); [FSE 2024 Test of Time](https://2024.esec-fse.org/info/awards)). The honest counterweight: later work found only 9.92% of individual mutants strongly coupled to real faults, with at least one strongly coupled mutant for 51.03% of faults ([Gay and Salahirad, ICST 2023](https://ieeexplore.ieee.org/document/10132183/)) — support for selective use, never for a score target.

**In practice.** Two tiers, because the economics differ by orders of magnitude. _Tier 1, universal_: a demonstration per new or materially changed load-bearing assertion, at authoring time, witnessed in review — full-suite runs are expensive, this is nearly free. _Tier 2, where blast radius justifies it_: continuous diff-scoped mutation analysis, mutating changed lines only, filtering arid lines, capping surfaced mutants per review, triaging each survivor as a missing test, a weak oracle, or an accepted gap. **Never gate on a mutation score**; a percentage re-imports the Goodhart failure of coverage one level up. Mechanize the demonstration where the harness allows, because "I ran it and it went red" is testimony and a recorded red run is evidence.

Four traps, all cheap to avoid. **Red for the wrong reason is not evidence.** If the mutation breaks the program before the assertion runs, you have learned nothing. Prefer behaviour-preserving mutations — change what the assertion reads and nothing else — and require the failure output to name the specific check. **Invalidate caches.** Compiled-artifact caches keyed on (mtime, size) will happily reuse stale bytecode when a mutation is applied and reverted inside one clock tick with no length change. The failure direction is the dangerous one: a live assertion reported as vacuous — a false all-clear from the tool built to prevent false all-clears. **Equivalent and optimization-only mutants are the tax**, not findings; SQLite skips them by source annotation, marking branches that help the code run faster without changing output, and a standard without that escape hatch teaches engineers to assert on incidental behaviour. **Unexecuted assertions** are the cheapest vacuity mode of all — skipped by tag drift, stranded after an early return, inside a callback that never fires; count executed assertions where you can and treat zero as failure.

**Prevents.** The vacuous test in all its forms; assertions that test the mocking framework; false all-clears from the calibration tool itself; equivalent-mutant whack-a-mole; testimony in place of evidence.
## 5. For "nothing changed" claims, use generated evidence — not more examples.

When the promise is _this refactor changed nothing_, or _these two paths agree_, examples are the wrong instrument. Run both implementations on generated input and compare. Generally: **when the promise quantifies over inputs — for all, never, always agrees — the test must quantify over inputs.** Examples are for promises about points; generated evidence is for promises about spaces.

Four instruments, weakest machinery first. _Cross-branch differential_: the pre-change system is the reference — worktree the old branch and assert `ref.f(x) == new.f(x)` over generated inputs ([Wayne, cross-branch testing](https://www.hillelwayne.com/post/cross-branch-testing/)). _Independent-implementation differential_: two implementations of one spec, the technique McKeeman named in 1998 for compilers ([Differential Testing for Software](https://www.semanticscholar.org/paper/Differential-Testing-for-Software-McKeeman/fc881e8d0432ea8e4dd5fda4979243cac5e4b9e3)) and SQLite institutionalized across five SQL engines ([SQLite testing docs](https://www.sqlite.org/testing.html)). _Property testing_: state an invariant and generate inputs to refute it, from QuickCheck ([Claessen & Hughes, ICFP 2000](https://www.cis.upenn.edu/~bcpierce/courses/552-2008/resources/icfp-quickcheck.pdf); [ACM](https://dl.acm.org/doi/10.1145/351240.351266); [Hughes on specification-based testing](https://www.cs.utexas.edu/~hunt/FMCAD/fmcad11/papers/inv8.pdf)) to Hypothesis ([JOSS 2019](https://joss.theoj.org/papers/10.21105/joss.01891)), with a taxonomy for finding the properties themselves — invariants, round-trips, idempotence, oracles, commutativity ([Finding Property Tests](https://www.hillelwayne.com/post/contract-examples/); [what is property-based testing](https://hypothesis.works/articles/what-is-property-based-testing/)). _Metamorphic testing_: where no single-output oracle exists, assert relations between outputs of related inputs — `f(shuffle(xs)) == f(xs)`, adding a filter never increases result count — where even ad hoc relations approach the fault-detection power of a true oracle ([Wayne](https://www.hillelwayne.com/post/metamorphic-testing/); [Chen et al., TSE 2014](https://www.computer.org/csdl/journal/ts/2014/01/06613484/13rRUNvya2K); [Segura et al.](https://eprints.whiterose.ac.uk/id/eprint/110335/1/segura16-tse.pdf)).

**In practice.** State the quantified claim before choosing a tool, and classify the generated corpus so that "10,000 cases" cannot mean 9,999 empty strings. Three ergonomics are non-negotiable, because teams that skip them try generative testing once and abandon it. **Seeds are logged outside the test process**, so a crash cannot take the reproducer with it; run once with a fixed seed for CI reproducibility and again with a random seed so coverage accumulates ([TigerBeetle, A Tale of Four Fuzzers](https://tigerbeetle.com/blog/2025-11-28-tale-of-four-fuzzers/)). **Shrinking is mandatory**: a property test reporting a 40 KB counterexample has found a bug and hidden it in the same gesture, and automatic reduction is the feature that made generative testing adoptable ([Hypothesis, JOSS](https://joss.theoj.org/papers/10.21105/joss.01891.pdf); [MacIver & Donaldson, ECOOP 2020](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ECOOP.2020.13); [notes on reduction](https://drmaciver.com/2019/01/notes-on-test-case-reduction/)). **Every minimized counterexample is promoted into the permanent corpus**, exactly as SQLite's `fuzzcheck` re-runs every historically interesting case on every full test pass. Keep a few named examples beside the generators; they are the readable specification.

State the two characteristic lies of differential oracles. **Correlated failure**: two implementations sharing a misreading of the spec agree with each other and are both wrong, which is why differential testing complements rather than replaces examples written from the spec. **Bug-for-bug lock-in**: the reference is sometimes wrong, and the harness will faithfully freeze its bug into the new implementation; when old behaviour is deliberately changed, the differential test is retired or re-scoped in the same commit, or the suite starts enforcing behaviour nobody wants.

**Prevents.** False confidence in "nothing changed" refactors, the most common lie in software maintenance; example suites that sample the input space three times and call it covered; irreducible counterexamples; lost seeds; frozen bugs.
## 6. Every assertion names its oracle.

Every test declares, by construction, where its expected value comes from. The author answers in one sentence; the reviewer checks the answer. The oracle problem is the oldest unsolved problem in testing and the one most standards ignore: the canonical survey catalogues specified, derived, pseudo-, and human oracles, and observes that most real systems have no complete oracle and must assemble partial ones ([Barr, Harman, McMinn, Shahbaz & Yoo, IEEE TSE 2015](https://dl.acm.org/doi/10.1109/TSE.2014.2372785)).

The hierarchy, strongest first. **(1) Specified** — written from a requirement, independently of the implementation; the only oracle that can catch a spec-interpretation bug, and what Beck's _predictive_ desideratum demands ([Test Desiderata](https://medium.com/@kentbeck_7670/test-desiderata-94150638a4b3)). **(2) Derived** — a reference implementation, a worked example from a standard, a paper's vectors. **(3) Invariant or relational** — properties and metamorphic relations: partial oracles that catch classes of wrongness without knowing any right answer. **(4) Pseudo/differential** — the old version, another engine. **(5) Change detection** — goldens, snapshots, approvals, where the oracle is "whatever the code does today."

**In practice.** Put a one-line oracle note on any non-obvious test: "expected from RFC section 4.2," "checked against arbitrary-precision model," "provider contract v3," "linearizability checker." Prefer a small, slow, obviously correct reference model to a duplicate of the production implementation, and never call the same normalization helper on expected and actual. **Class-5 oracles must be labeled** and confined to subsystems where nothing better exists — rendered output, wire formats, compiler diagnostics — and governed by Rule 17. Tests in classes 1 to 3 are worth more than tests in classes 4 and 5 and are protected accordingly in review. A test whose oracle is "the code, obviously" is usually a tautology: the test that re-implements the function and asserts the function equals its re-implementation. The payoff is diagnostic — when a class-1 test fails the code is wrong; when a class-5 test fails, something _changed_ and a human must adjudicate. A suite that cannot tell you which kind of red it is has no epistemology, only a pass rate.

**Prevents.** The tautological test; oracle laundering, where a snapshot is presented as a specification; goldens generated from the current build and accepted unread; the suite that cannot distinguish wrong from different.
## 7. Determinism is constructed, not assumed.

A test may not consult the wall clock, the network, ambient randomness, thread scheduling, or ambient identity unless the harness has explicitly supplied and logged a controlled substitute. Every source of nondeterminism enters through a seam, and every seam's default is deterministic.

Fowler states the stakes in one sentence: non-deterministic tests "are useless" and "a virulent infection that can completely ruin your entire test suite" — useless because a failing run proves nothing, virulent because engineers learn to re-run instead of investigate; his taxonomy of causes (isolation, asynchrony, remote services, time, resource leaks) has held for fifteen years ([Eradicating Non-Determinism in Tests](https://martinfowler.com/articles/nonDeterminism.html)). Taken to its endpoint the rule becomes deterministic simulation testing, which Jepsen defines as "essentially property-based testing with techniques to turn non-deterministic systems into deterministic ones. The clock, disk state, scheduler, network delivery, external services, and so on are controlled to ensure reproducibility" ([Jepsen: TigerBeetle 0.16.11](https://jepsen.io/analyses/tigerbeetle-0.16.11)).

**In practice.** Five seams, each with a stack-agnostic default. _Time_: inject a clock, default to a fixed epoch, use monotonic time for durations. _Randomness_: inject the generator, fix the seed, print it on failure. _Scheduling_: where concurrency is under test, drive it explicitly (Rule 14); elsewhere prefer synchronous doubles to real threads, and never a bare sleep as synchronization — wait on a condition. _Environment_: no test reads `$HOME`, DNS, locale, or timezone unless the harness set it. _Identity_: uuids, monotonic ids, and temp paths come from a harness-controlled generator. The pattern that makes all five cheap is the one Rule 1 already mandates — the port; a port for time is one interface and its deterministic adapter is twenty lines, which is the observation that hermeticity is Rule 1 applied to the operating system. Retrofitting is where the rule bites: a codebase calling `now()` in 900 places will not adopt a clock port in one PR, so grandfather it with an allowlist of call sites that shrinks monotonically, ratcheted in CI. The compounding payoff justifies over-investing here: a codebase hermetic at the unit level is _simulable_ at the system level, and simulation is where the expensive bugs live — FoundationDB's simulator let its authors re-run even the weirdest and rarest bugs from the same seed until fixed ([Antithesis](https://antithesis.com/blog/is_something_bugging_you/)), and TigerBeetle reproduces any run from `vopr -- <seed>` ([HACKING.md](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/internals/HACKING.md)).

**Prevents.** The Heisenbug that reproduces only in CI at 2 a.m.; the suite that is green when re-run, the single most corrosive artifact in the false-alarm economy; claims of determinism with no recorded seed, clock, binary, or schedule. _Of the rule itself_: over-abstraction — one seam per nondeterminism source actually consulted, not per source imaginable.
## 8. Hermetic by default: the test controls everything it observes.

A test run's result may depend only on the code under test, its checked-in inputs, and the harness. Tests create what they need in a sandbox they own and destroy it. A test that can be perturbed by another test on the same machine, or by the state of the world outside the repository, is defective.

_SWE at Google_ defines hermetic tests as running in an environment entirely self-contained, yielding "greater determinism... and isolation," and names the residual enemies: system time, random number generation, race conditions ([ch. 23](https://abseil.io/resources/swe-book/html/ch23.html)). The hermetic-server pattern is the recipe for service tests: bring the dependency up in a box on loopback with no connection to the real world ([Hermetic Servers](https://testing.googleblog.com/2012/10/hermetic-servers.html)). The violation that bites most often is not a server but the shared mutable fixture: Luo et al.'s study of flaky-test fixes found test-order dependency among the top three root causes, behind only asynchronous waits and concurrency ([FSE 2014](https://mir.cs.illinois.edu/lamyaa/publications/fse14.pdf)).

**In practice.** Four enforcement points. _Scratch space_: a fresh temp directory, schema, or namespace per test, created in setup and destroyed in teardown, with parallel workers partitioned by index. _No ambient network_: CI blocks egress or stubs it at the socket layer, so a test reaching for the internet fails loudly instead of passing slowly. _No shared mutable state_: fixtures are constructed per test from builders with valid, boring defaults and named overrides, so any override in a body signals what the test depends on ([Nat Pryce, Test Data Builders](http://www.natpryce.com/articles/000714.html)); a fixture edited for test 41 silently re-specifies tests 1 through 40. _Namespacing_: servers bind port 0 and read back the assignment; nothing hardcodes 8080. The rule forbids sharing _state_, not _infrastructure_ — a shared container with per-test transactional rollback or snapshot restore preserves isolation cheaply. Share what is a contract: conformance vectors, protocol suites, fuzz corpora, immutable canonical data, versioned and sourced. Do not share code that merely sets a scene. The subtle modern violation is the test hermetic on a laptop and not in CI, sensitive to a shell rc file, a Docker version, or a case-insensitive filesystem; the cheapest detector is a periodic job running the suite in a minimal container with a randomized environment.

**Prevents.** Order-dependent tests, green serially and red under `-j8`; the entire "works on my machine" class; runs whose outcome encodes which other jobs shared the worker; the Mystery Guest fixture loaded from a distant file.
## 9. Every test carries a size class with enforced resource ceilings, and every suite has a latency budget.

Small: single process, no network, no database, no filesystem, no threads, no sleeps. Medium: one machine, loopback only. Large: everything else. Google's taxonomy defines the classes by resource ceilings rather than intent, with 60/300/900-second limits ([Test Sizes](https://testing.googleblog.com/2010/12/test-sizes.html)), and separates _size_ — resources, processes, time — from _scope_, advising the smallest test that can address the risk ([ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)). The empirical stick is the flakiness gradient over one week: 0.5% of small tests, 1.6% of medium, 14% of large were flaky ([Where do our flaky tests come from?](https://testing.googleblog.com/2017/04/where-do-our-flaky-tests-come-from.html)). The small tier dominates not for aesthetics but because speed and determinism are the gate-compatible properties.

**In practice.** Enforce sizes with the sandbox, not the style guide: a "small" test that opens a socket _fails_, which makes violations loud instead of statistical. Budgets are gates the same way — a test exceeding its class budget fails as a test failure, because a slow suite is an unrun suite. One deliberate deviation from Google is warranted: 60 seconds is far too generous on a modern machine, so budget small tests in milliseconds and the small tier in seconds to low minutes, declared as an SLO with alerting, exactly like a production latency objective. Feedback latency compounds into behaviour and changes what engineers _do_ more than what they ship. Stage the rest rather than omitting it: small on every commit, blocking merge; medium pre-merge; large, sanitizer, platform-matrix, long fuzz, mutation, fault campaigns, and performance work on schedule with declared rather than denied flake rates ([Fowler on the commit suite](https://martinfowler.com/bliki/UnitTest.html)). Guard the ratchet with p95 latency per class, which cannot be gamed by relabeling a slow test "medium." The invariant: every behaviour is tested at the smallest size at which it can be honestly expressed, and nothing is tested at two sizes without a reason.

**Prevents.** The monolithic unclassified suite where every test pays the slowest test's schedule; the ice-cream cone and the hourglass; E2E accretion into the 14%-flaky tier; the forty-minute suite that runs after lunch instead of before merge.
## 10. Flakiness has a policy: out of the gate the same day, with an owner and an expiry, and never retried into green.

A flaky test is a bug in the test or in the system, never a fact of nature. A test whose outcome varies across runs of an unchanged build does not gate changes as if it were trustworthy.

Google measured roughly 1.5% of all test runs as flaky, with almost 16% of tests exhibiting some flakiness, and built automation that monitors and automatically quarantines while filing a bug — noting candidly that flaky-tolerance mechanisms "encourage developers to ignore flakiness in their own tests," which is the trap ([Flaky Tests at Google](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)). Fowler supplies the doctrine: quarantine immediately so the flake stops destroying signal, "but fix quarantined tests quickly" ([Eradicating Non-Determinism](https://martinfowler.com/articles/nonDeterminism.html)). Luo et al. supply the fix targets: asynchronous waits, concurrency, and order dependency dominate real causes ([FSE 2014](https://mir.cs.illinois.edu/lamyaa/publications/fse14.pdf)).

**In practice.** Five clauses, each chosen because the naive alternative fails. _Detection is statistical_: run new and changed tests repeatedly, shuffled and in parallel with themselves, before they may gate, and re-run gating failures on the same revision to classify them. _Quarantine removes the test from the gate, not from the record_: it still runs, still reports, and its failures still count toward its owner; a quarantine that hides results is a deletion with extra steps. _Expiry_: an owner and a fix-by date of two to four weeks, after which the entry becomes a fix or a deletion; an unowned quarantine is deleted on arrival, because an unowned flaky test is a bug nobody intends to fix. Google's own engineers noted auto-quarantine "could easily mask a real race condition," which is exactly why the deadline ends in root cause or removal and never in silent permanence. _No retry-to-green at the gate_: a test that needed a retry has already told you it can lie; retries are instrumentation only, with the count reported rather than absorbed and the first failure preserved. _The flake budget is a number_: "fewer than 0.5% of small-test runs flaky" is enforceable; "flakiness matters" is a sentiment. Quarantine only the smallest failing unit, and treat every flake as a bug report about the _system_ until proven otherwise — a race in a harness and a race in production look identical from outside.

**Prevents.** Alert fatigue and the re-run culture in which red stops being a signal; real regressions hiding inside a noise band; the permanent allow-failure lane. _Of the rule itself_: the graveyard quarantine, which is how suites silently lose their riskiest coverage.
## 11. Coverage is an inspection instrument, never an objective.

Coverage is collected and surfaced at review time to answer one question: what did we not exercise? No coverage percentage is a merge gate or a team target.

The strongest empirical result in the field: Inozemtseva & Holmes measured statement, decision, and modified-condition coverage against mutation-measured fault detection across 31,000 suites and five large systems, found low to moderate correlation once the number of test cases is controlled for and no additional insight from stronger criteria, and concluded coverage "should not be used as a quality target because it is not a good indicator of test suite effectiveness" ([ICSE 2014](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf)) — awarded ICSE's Most Influential Paper a decade later precisely for moving the field off targets ([UBC](https://www.cs.ubc.ca/award/2024/04/icse-most-influential-paper-award)). Fowler's formulation is exact: coverage finds untested code and is "of little use as a numeric statement of how good your tests are" ([Test Coverage](https://martinfowler.com/bliki/TestCoverage.html)). Google's coverage system, processing a billion lines a day, deliberately surfaces coverage _at the changeset level during code review_ rather than as a gate ([Ivanković et al., FSE 2019](https://homes.cs.washington.edu/~rjust/publ/google_coverage_fse_2019.pdf); [Code Coverage Best Practices](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html)), and names the perverse outcome of the alternative: "instead of treating 80% like a floor, engineers treat it like a ceiling," abandoning the remaining 20%, which is by construction the error handling. The category error at the core: coverage "only measures that a line was invoked, not what happened as a result" ([ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)) — the vacuous test one level up, an oracle gap executed code can preserve indefinitely ([Parsai et al.](https://par.nsf.gov/servlets/purl/10555509)). Beck supplies the economy: "I get paid for code that works, not for tests, so my philosophy is to test as little as possible to reach a given level of confidence" ([Beck](https://stackoverflow.com/questions/153234/how-deep-are-your-unit-tests)).

**And yet SQLite maintains 100% branch and MC/DC coverage, so the standard must reconcile it, because a principal engineer will raise it.** Two halves. First, SQLite's 100% is not a target on application code; it is a completeness proof over a frozen kernel — 155.8 KSLOC of C defended by roughly 590 times as much test code, where the coverage run is itself "a test of the test — a meta-test," and where SQLite says outright that maintaining 100% MC/DC is laborious and "probably not cost effective for a typical application" ([SQLite testing docs](https://www.sqlite.org/testing.html)). Second, and less often quoted: SQLite documents that 100% MC/DC is _in tension_ with fuzz robustness, because MC/DC punishes defensive unreachable branches, so code tuned for MC/DC "tends to be more vulnerable to problems found by fuzzing." The maximalist case therefore concedes the point — coverage is a means with trade-offs, chosen per component and paired with fuzzing to cover the branches it discourages.

**In practice.** Three legitimate uses: _diff coverage in review_, where changed lines with zero execution are displayed and a human decides whether it matters — an uncovered new error handler is a conversation, an uncovered comment is not; _archaeology_, where periodic whole-repo maps locate untested subsystems and feed risk assessment rather than compliance; and _meta-testing_, where a coverage number dropping on unchanged source means the _suite_ changed, exactly the signal a passing percentage would bury. Diff coverage may be a review signal and at most a soft local gate chosen by a component's owners; project-wide percentage targets never. Coverage tells you where tests are not; mutation tells you whether tests work; never let the first impersonate the second.

**Prevents.** Coverage theatre — assertion-free tests written to move a number; the 80%-as-ceiling effect; a repository average masking zero coverage in the one component that matters; rejection of valuable black-box tests because they add no new lines.
## 12. Every bug fix ships with a test observed red on the unfixed code.

SQLite states it as policy: "When a bug is reported against SQLite, that bug is not considered fixed until new test cases that would exhibit the bug are added" to the suite ([SQLite testing docs](https://www.sqlite.org/testing.html)). _SWE at Google_ states it as the third kind of change: the bug suggests a case was missing from the initial suite, and the fix should include it ([ch. 12](https://abseil.io/resources/swe-book/html/ch12.html)). Fowler states it as ordinary practice — write the test that exposes the bug, then fix it; no bug is properly fixed without an automated regression test ([Self-Testing Code](https://martinfowler.com/bliki/SelfTestingCode.html); [Goto Fail, Heartbleed, and Unit Testing Culture](https://martinfowler.com/articles/testing-culture.html)).

The epistemology is the point. A bug is an experimentally confirmed hole in the suite: the one moment you possess a guaranteed-non-vacuous test, pre-verified against reality, and declining it discards evidence. The red must be observed _on the unfixed code_, not asserted afterwards — a test written after the fix that "would have failed" is a counterfactual claim, and teams routinely discover their reproduction was wrong the moment they are forced to show red. A bug fix whose test never went red is an unverified hypothesis about causation. This is the one place where ordering, not merely calibration, is mandated.

**In practice.** The PR contains the failing test in one commit and the fix in the next, or a CI-verifiable attestation that the test is red on the parent commit. The test encodes the correct behaviour at the boundary (Rule 1), never the internal mechanism of this fix — otherwise the regression test dies in the next refactor while the bug's whole equivalence class survives. Fix the class, not only the instance: one example for the reported case plus a property or boundary sweep for its family, because bugs cluster at the boundaries the original tests did not imagine. Where the trigger was generative, the shrunk counterexample and its seed are promoted into the permanent corpus.

**The carve-out, honestly stated.** Irreproducible failures — Heisenbugs, environment-specific faults, crashes without dumps — cannot be pinned on demand, and forcing a test anyway produces one that never went red, vacuous by construction, or delays an obviously correct fix behind an impossible reproduction. The obligation converts rather than disappears. **Instrument**: add the invariant assertions, state checks, and logging that would make the next occurrence self-reporting, which is why TigerBeetle hash-chains replica histories so rare faults leave forensic evidence ([TigerBeetle docs](https://docs.tigerbeetle.com/single-page/)). **Expand exploration**: more interleaving coverage (Rule 14), more fuzzing time, a wider fault matrix (Rules 13 and 15). Such bugs remain open as _suite deficiencies_ until the mechanism is understood, and the waiver is a written artifact naming what was tried, so "couldn't reproduce" becomes reviewable rather than ambient. "Too trivial," "hard to test," and "the patch is obvious" are not carve-outs.

**Prevents.** Regressions walking back in through the same hole; the mechanism-pinned regression test that dies at the next refactor; folklore in place of suite state.
## 13. Fuzz what parses; property-test what transforms; keep the corpus as a permanent asset.

Every parser, decoder, deserializer, codec, frame handler, file-format reader, and query front end that accepts input across a trust boundary is fuzzed continuously. Every total transformation — round-trips, normalization, encoding, compiler passes — is property-tested for its invariants. Crash-level findings gate the release; historical counterexamples are checked in.

The yield is measured in five figures: as of May 2025, OSS-Fuzz has helped identify and fix over 13,000 vulnerabilities and 50,000 bugs across 1,000 projects ([OSS-Fuzz](https://github.com/google/oss-fuzz)), running on the order of ten trillion inputs a day within months of launch ([Google Security Blog](https://security.googleblog.com/2017/05/oss-fuzz-five-months-later-and.html)). The economising technique is coverage guidance — retain inputs reaching new control-flow edges, then mutate them further ([AFL](https://github.com/google/AFL/blob/master/README.md); [repository](https://github.com/google/afl)) — which SQLite credits as the first practical profile-guided fuzzer; its structure-aware `dbsqlfuzz`, mutating SQL text and database file simultaneously at roughly a billion cases a day, is where most of SQLite's testing CPU now goes, with the result that external fuzzer reports "have all but stopped" ([SQLite testing docs](https://www.sqlite.org/testing.html)).

**In practice.** Scope by input surface, not fashion: a CRUD handler behind a validated schema mostly does not need a fuzzer, a hand-written decoder always does. Targets live with the source and build with the tests so they cannot rot, run under sanitizers with assertions enabled, and start from a seed corpus and a dictionary ([OSS-Fuzz ideal integration](https://google.github.io/oss-fuzz/advanced-topics/ideal-integration/)). Strengthen the oracle past "does not crash" wherever possible: parse-print-parse fixpoints, `decode(encode(x)) == x`, two decoders that must agree. This is the boundary case worth naming — fuzzing finds robustness bugs cheaply and correctness bugs only where an oracle exists, so a parser that silently accepts invalid input is invisible to a crash oracle, which is why differential fuzzing against a second implementation is the premium configuration and why SQLite singles out the fuzzers that find wrong _answers_ rather than crashes. The corpus has a lifecycle: minimize, deduplicate, check in, and replay in CI as cheap regression coverage on machines that never run the fuzzer. A serialization round-trip property is the highest-value ten lines in most codebases.

**Prevents.** The parser as attack surface and uptime risk; the round-trip bug found by the first customer with non-ASCII data; "fuzzing" with uniform random bytes that never pass a header. _Of the rule itself_: fuzz-infrastructure rot, since a fuzzer no CI runs is decoration, and corpus bloat, which is why the corpus is managed rather than appended forever.
## 14. Concurrency is tested by exploring interleavings, never by stress-and-pray.

Concurrent code is tested with systematic interleaving exploration or deterministic simulation, in which the harness controls scheduling decisions and records the schedule of every run. Looping a racy workload and hoping is not a concurrency test; it is a coin flip with a CI budget.

The existence proof is CHESS: a systematic tester enumerating interleavings with fair scheduling and bounded preemption, producing repeatable traces, which "reproduce[d] in thirty seconds a Heisenbug that appeared just once in months of testing" ([Musuvathi et al., OSDI 2008](https://www.usenix.org/event/osdi08/tech/full_papers/musuvathi/musuvathi.pdf)). The generalization is deterministic simulation as FoundationDB and Antithesis industrialized it — run the system in a deterministic simulated environment, feed controlled entropy, explore states, check invariants ([Antithesis on DST](https://antithesis.com/docs/resources/deterministic_simulation_testing/); [how it works](https://antithesis.com/docs/introduction/how_antithesis_works/)) — and TigerBeetle's VOPR, which runs a whole cluster single-threaded from one seed, where "3.3 seconds of VOPR simulation gives you 39 minutes of real-world testing time... a day gives you 2 years" ([TigerBeetle](https://tigerbeetle.com/blog/2023-07-11-we-put-a-distributed-database-in-the-browser/); [docs](https://docs.tigerbeetle.com/single-page/); [HACKING.md](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/HACKING.md)). The indictment of the default is Luo et al.: concurrency and asynchronous waits are the top two causes of real-world flaky tests ([FSE 2014](https://mir.cs.illinois.edu/lamyaa/publications/fse14.pdf)). The industry is not short of CPU hours; random interleaving sampling is simply astronomically less efficient than systematic exploration.

**In practice.** A four-rung ladder; be on the highest rung the architecture supports. **Rung 1, available everywhere**: make concurrency controllable by injecting executors and dispatchers as ports (Rule 7), so "concurrent" code runs deterministically on one thread with explicit interleaving points. **Rung 2, the cheapest real upgrade**: a seeded scheduler exploring a different order per run and recording the seed, which subsumes stress testing strictly — same statistical coverage, plus reproducibility. **Rung 3**: systematic exploration, model checking or CHESS-style enumeration with preemption bounding, scoped to the concurrency core — the lock-free queue, the protocol state machine ([Loom](https://github.com/tokio-rs/loom)). **Rung 4**: full deterministic simulation with fault injection, and where the system cannot be made deterministic, external history checking against a formal consistency model in the Jepsen style ([Jepsen](https://jepsen.io/analyses)). Three corollaries. State safety ("no acknowledged write is lost," "at most one owner") and _liveness_ ("a healthy quorum eventually makes progress") separately; liveness is tested by divergence detection during exploration, not by hoping a hang happens while someone is watching. Race detectors are necessary and insufficient — ThreadSanitizer finds data races and by design says nothing about linearizability or deadlock freedom ([ThreadSanitizer docs](https://clang.llvm.org/docs/ThreadSanitizer.html)) — so detector silence is not an argument about algorithm correctness. And every failure carries its schedule or seed, because a concurrency bug without a reproducer is a rumour. State-space explosion is real even with bounding; exhaustiveness is a budget, not a religion.

**Prevents.** The Heisenbug that takes months to reproduce; the load test cosplaying as correctness evidence; production-only races; partition testing with no consistency oracle; safety-only testing that permits permanent unavailability.
## 15. Every durability or recovery promise is tested by seeded fault injection.

If the system claims to survive a crash, a full disk, a torn write, an allocation failure, a timeout, a cancellation, or a restart, those faults are injected on a schedule from a seed, and the failure artifact is the seed.

SQLite's single-node discipline is its least famous and most impressive: a rigged VFS that simulates crashes mid-write and reorders unsynced writes, an instrumented allocator that fails at allocation N iterated over all N, and — the part intuition never reaches — _stacked_ faults, "an I/O error or OOM fault that occurs while recovering from a prior crash." SQLite has a reputation for robustness against these failures because the failures are tested rather than hoped against ([SQLite testing docs](https://www.sqlite.org/testing.html)). Jepsen is the distributed counterpart: injected partitions, pauses, and clock skew with history checking find lost acknowledged writes and read skew in mature databases whose own tests were green ([Jepsen analyses](https://jepsen.io/analyses)).

**In practice.** Rung 1 of Rule 14's ladder is implementable in an afternoon on any codebase that obeyed Rules 1 and 7: fault-injecting fakes at the ports — an allocator that fails on schedule, a filesystem that tears writes, a network that drops and reorders — driven in a loop that advances the failure point one step at a time until the operation completes cleanly, with an integrity check after every iteration. That is SQLite's exact loop. Above it, stateful property testing generates operation sequences against the real system and a trivial model and compares; above that, simulation. Maintain a **fault matrix** per subsystem — fault type crossed with system phase — and review it for un-exercised cells including stacked faults, because a matrix beats intuition and humans do not spontaneously imagine a crash during recovery. Recovery-point and recovery-time promises are ordinary behavioural assertions with numbers in them. Runbooks never executed are not evidence.

**Prevents.** The recovery path that has never been executed; corruption on power loss; the retry storm discovered in production; graceful-degradation claims that are marketing.
## 16. Performance tests are controlled experiments, not timings.

A performance test states a hypothesis, controls or randomizes its confounders, reports distributions rather than point estimates, and treats its own measurement infrastructure as suspect until validated. A benchmark whose result can be flipped by link order is not a measurement; it is a sample from an uncharacterized distribution.

The scandal of systems measurement is Mytkowicz et al.: changing UNIX environment size or the link order of object files — changes with no conceivable semantic effect — swung results enough to flip the sign of an optimization's measured benefit, hence _Producing Wrong Data Without Doing Anything Obviously Wrong_ ([ASPLOS 2009](https://dl.acm.org/doi/10.1145/1508284.1508275)). For latency, Gil Tene's coordinated-omission work shows the standard load-generator architecture systematically deletes the worst samples from the record — a stalled server delays the generator's next request, omitting exactly the backlog that hurt users — with prescriptions worth adopting verbatim: do not derive from standard deviation, always measure max, measure many percentiles, and "whatever your measurement technique is, test it" ([How Not to Measure Latency](https://qconsf.com/sf2012/dl/qcon-sanfran-2012/slides/GilTene_HowNotToMeasureLatency.pdf)). Harness documentation catalogues the rest of the variance — frequency scaling, placement, SMT, cache effects, NUMA ([Google Benchmark, Reducing Variance](https://google.github.io/benchmark/reducing_variance.html)).

**In practice.** Five clauses. _Distributions, not points_: report p50/p90/p99/max; a p99 regression with a flat median is invisible to a mean-based gate. _Control or randomize confounders_: pin the machine class, disable frequency scaling and noisy neighbours where you can, randomize run order, and where the environment cannot be controlled — shared CI — compare **ratios against a same-run baseline** rather than absolute numbers across runs. _The gate is a regression test, not an absolute bar_: flag regressions beyond a declared tolerance on the same hardware class, generous enough that natural variance cannot trip it, because absolute thresholds rot as hardware drifts. _Validate the harness_: calibrate the load generator against a known-fixed-latency service and check the recorded distribution matches, and confirm the benchmark can see a regression by running a deliberately pessimated build — Rule 4 applied to the least-calibrated test category in most organizations. _Budget the runtime_: performance work lives in the scheduled tier, because a benchmark suite gating every commit is the first thing engineers disable. The honest downgrade is permitted and labeled: coarse same-run-relative smoke benchmarks for per-commit trend signal, controlled experiments for release gates and suspicious trends.

**Prevents.** Regression blindness as fifteen individually innocent PRs land a 15% p99 regression; optimization decisions driven by link order; latency dashboards that omit precisely the pain they exist to measure; a perf suite that becomes the flakiest thing you own.
## 17. Golden files and snapshots live under re-baseline discipline.

Every golden or snapshot artifact is minimized to the behaviour it guards, canonicalized to remove incidental variation, and re-baselined only through reviewed diffs. A bulk "update all snapshots" commit is a defect in the process, not a convenience.

A snapshot is the class-5 oracle of Rule 6: its expected value is the implementation's own current output, so its entire evidentiary content is the human review of the diff. Unreviewed, it inverts the ideal-test property — it changes on every diff, engineers rubber-stamp updates, and the test degrades into a change detector with extra steps. The canonical account of the failure mode is developers under time pressure nuking the snapshot and recording a fresh passing one, converting the suite into a machine that ratifies whatever the code currently does; the remedies — keep snapshots small, avoid huge serialized blobs, pair them with targeted behavioural assertions — are this rule's clauses ([Kent C. Dodds on snapshot testing](https://kentcdodds.com/blog/effective-snapshot-testing)). Google adds that exact diffs over pixel layouts or log text should be narrowed toward meaningful semantics ([Stop Writing Brittle Tests](https://testing.googleblog.com/2024/04/how-i-learned-to-stop-writing-brittle.html)). The mature governance model is the browser-engine tradition: WebKit's and Chromium's expectation files make every accepted deviation enumerated, classified, owned, and bug-linked, and — the detail worth stealing — maintain **symmetry**, so a test that unexpectedly starts _passing_ also fails until the expectation file is updated ([WebKit TestExpectations](https://trac.webkit.org/wiki/TestExpectations); [Chromium expectation files](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/docs/testing/expectation_files.md)).

**In practice.** Four clauses, tooling-independent. _Minimize_: snapshot the smallest artifact carrying the behaviour — the error message, not the stack trace; the relevant subtree, not the whole render tree — because incidental surface area is incidental breakage. _Canonicalize_: strip timestamps, absolute paths, pointer values, hash-order iteration, and line-ending differences before capture; a golden that varies by machine is a flakiness generator wearing a different hat. _Re-baseline is a review event_: regenerated artifacts land with the change, the diff is small enough to read, the reviewer reads it, and regeneration tooling is deliberately inconvenient enough to force reading; a diff too large to review is a signal to split the test, not to skim faster. _No bulk re-baselines_: mass updates are decomposed per behaviour or accompanied by Rule 3's declaration — if the change is a refactoring, snapshots must not move at all, and a snapshot that moves during a refactoring _is the bug report_. Goldens are legitimate only where the full artifact is the contract: wire formats, code generation against a spec, compiler diagnostics, rendered documents. **Known failures are pinned, not commented out**: a reproduced-but-unfixed bug becomes an XFAIL test asserting the correct behaviour, with an owner, a bug link, an expiry, and inverted semantics — an unexpected pass is a failure that forces promotion to a gating test. An XFAIL ledger is a debt register; a commented-out test is a landfill. XFAIL is distinct from quarantine: quarantine is for tests whose verdicts are untrusted, XFAIL verdicts are trusted and inverted.

**Prevents.** Approval fatigue and the nuke-and-record culture — false confidence at industrial scale; environment-coupled goldens; the refactoring that silently changed output because snapshots were re-blessed in bulk; known issues living in folklore instead of suite state.
## 18. Test code is production code, with recorded deletion criteria.

Test code is reviewed as rigorously as production code and optimized for a different target: obviousness over abstraction. And like production code it carries a maintenance cost that must be justified — a test whose value no longer exceeds its cost is deleted, with the criterion recorded.

_SWE at Google_ supplies the style: stick to straight-line code over clever logic and tolerate some duplication; "if you feel like you need to write a test to verify your test, something has gone wrong"; DAMP — Descriptive And Meaningful Phrases — outranks DRY; and the structural reason tests need _more_ discipline is that, there being no tests for the tests, they require manual review ([ch. 12](https://abseil.io/resources/swe-book/html/ch12.html); [ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)). Failure output is part of the contract: a good message expresses the desired outcome, the actual outcome, and the relevant parameters, well enough that investigation can begin from the name and the message alone ([Test failures should be actionable](https://testing.googleblog.com/2024/05/test-failures-should-be-actionable.html)). Beck's twelve desiderata are the aspiration — isolated, composable, fast, inspiring, writable, readable, behavioral, structure-insensitive, automated, specific, deterministic, predictive ([Test Desiderata](https://medium.com/@kentbeck_7670/test-desiderata-94150638a4b3); [testdesiderata.com](https://testdesiderata.com/)) — with his caveat that they trade off, and that unit tests passing gives little confidence the system works while unit tests failing gives great confidence that it does not ([Desirable Unit Tests](https://newsletter.kentbeck.com/p/desirable-unit-tests)).

**In practice.** Style: names are sentences about behaviour; bodies are arrange/act/assert with no conditionals or ad-hoc loops (a loop over cases is the harness's parameterization, not control flow, and a conditional is two tests); assertions carry their subjects with structured diffs rather than bare booleans; setup uses builders, not shared mutable fixtures; any test with generated inputs, injected faults, or randomized order prints a one-line replay command with its seed. The balance-sheet clauses are the distinctive half. **Deletion criteria are declared in advance**: the behaviour it protects is deleted; it is subsumed by a stronger, cheaper test — an example subsumed by a property that would generate it, keeping the example only if it documents a scenario for readers; it passed its quarantine expiry; it is a class-5 artifact nobody can interpret any more; or it fails Rule 4's demonstration and nobody can say what it protects. **Deletion is recorded**: the commit names which criterion fired and where the displaced risk now lives, because deleting a test is a coverage decision. Deleting a red test to make CI green is not a criterion. **Suite cost is measured**: CI wall time per class, flakes per week, tests touched per refactoring, quarantine population and age, re-run rate, time-to-fix for a broken test. When those trend wrong the suite is telling you it is decaying, and the answer is curation, not more hardware. Trust is the real metric, so the suite reports on its own credibility quarterly to the engineers who stake releases on it — and its _metadata_ (quarantine entries, XFAIL pins, size declarations, expectation files) is a managed artifact under the same review, because that scaffolding is where policies go to die quietly.

**Prevents.** The suite as landfill, growing without curation; clever harnesses; fixtures shared by mutation; CI logs that say `expected false to be true` and nothing else; deletion anxiety, and its opposite, deletion as cleanup.
## 19. CI gates on trustworthy signals, and on nothing else.

Required tests run automatically on the smallest safe set of changes before integration. A failure blocks by default, names an owner, and is fixed, reverted, or waived by a time-bounded written risk decision. A broken mainline outranks feature work. A gate nobody believes is worse than no gate, because it institutionalizes override behaviour ([Fowler on Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html); [SWE at Google, ch. 23](https://abseil.io/resources/swe-book/html/ch23.html)).

**May gate**: the hermetic small and medium suites, green, no retries; Rule 4 demonstrations for new load-bearing assertions; the red-on-parent attestation for bug-fix tests; contract verification for cross-team surfaces, whose operationalized form is a deployability check against recorded consumer expectations ([Pact](https://docs.pact.io/university/introduction/step3)); crash-level fuzz findings; sanitizer failures; size-class and hermeticity violations; XFAIL symmetry breaches; egregious performance regressions against a same-run baseline with generous tolerance.

**May not gate**: whole-project coverage percentages; mutation scores; flaky large-suite results, which are quarantined instead; any metric whose natural variance exceeds its threshold; anything retriable into green. Diff coverage may be a review signal and at most a soft local gate chosen by a component's owners.

**In practice.** Dependency-aware test selection with periodic full-suite validation, because unvalidated selection is an untested optimization on your only safety net. Every target has an owner. Every failure emits command, seed, environment and build hash, logs, diffs, and minimized counterexamples. Waivers are explicit, approved, expiring, and linked to a risk. Release gates run the relevant full matrix, not the presubmit subset. And test observability is part of product testability: a distributed test that can detect "history invalid" but cannot expose operation ids, causal events, fault schedule, and persisted state is sensitive and operationally useless. Design diagnostic surfaces, invariant checks, and replay hooks as production capabilities; tests are their first client.

**Prevents.** Required checks retried into green; unowned failures; a red default branch for days; known-failure lists without expiry; selection gaps nobody measures.

Humans find; machines remember — as soon as exploratory testing finds an issue it becomes an automated test. Portfolio ratios are not mandated: required confidence is set by blast radius, which is why SQLite's answer (590x test-to-source, MC/DC on a frozen kernel, a billion fuzz cases a day) and a web application's answer differ by orders of magnitude while obeying the same standard. What is required is a one-page **risk map** per subsystem — top failure consequences, boundaries and owners, the oracle for each critical claim, the fault model, CI stage and budget, and explicitly accepted blind spots — reviewed quarterly so its rot is observable ([10 Minute Test Plan](https://testing.googleblog.com/2011/09/10-minute-test-plan.html); [SWE ch. 14](https://abseil.io/resources/swe-book/html/ch14.html); [ISO/IEC/IEEE 29119-1 on risk-based testing](https://wildart.github.io/MISG5020/standards/ISO-IEC-%20IEEE%2029119-1.pdf)). Ratios emerge from that map. Prose test plans enumerating cases are forbidden as redundant with the suite itself; a well-named suite _is_ the readable test plan, and Beck's Canon TDD step one — a live list of scenarios to cover — is the plan at the correct weight ([Canon TDD](https://newsletter.kentbeck.com/p/canon-tdd)).

## Reviewer checklist, ordered by kill rate

The first five items catch most of what matters. A "no" requires revision or a written risk decision.

**Calibration — does the test work at all?**

1. Was every new load-bearing assertion demonstrated able to fail, by witnessed red run or recorded mutation, and did the failure name the specific check? (4)

2. Is the oracle statable in one sentence — spec, reference, invariant, relation, change detector — and if a change detector, is the artifact minimized and the diff small enough to read? (6, 17)

3. If this is a bug fix: where is the test observed red on the unfixed code, or the written carve-out with instrumentation and expanded exploration? (12)


**Behavioural fidelity — does the test test what it claims?**

4. Does the PR declare its change kind, and does the test diff match? Refactorings move neither tests nor snapshots; only behaviour changes edit existing expectations. (3, 17)

5. Does the test enter through the narrowest contract boundary that owns the behaviour, rather than through internals or the outermost edge by default? If an internal needed testing, was it promoted to a module? (1)

6. Do assertions read observable outcomes at that boundary, with interaction assertions confined to interactions that cross the boundary and _are_ the behaviour? (2)

7. Do universal assertions harvest with a witness count, and are existentials enumerated deliberately? Are whole-object equality, ordering, ids, and timestamps asserted only where contractual? (2)

8. Does the name read as a sentence about behaviour, without "and"? Is the body straight-line, complete and concise? (3, 18)


**Environment — will it lie under load?**

9. Is it hermetic: owned scratch space, no ambient network, no shared mutable fixtures, no hardcoded ports, no bare sleeps? Does it pass alone, shuffled, and in parallel with itself? (8)

10. Are time, randomness, scheduling, environment, and identity reached only through seeded, logged seams? (7)

11. Is the size class declared and honest — would "small" survive the resource ceilings — and within budget? (9)

12. If a double replaced a dependency, is it verified against the real implementation by a shared contract suite, generated from a schema, or backed by record/replay? If not, why is the drift risk acceptable? (2)


**Economics — will it still be believed in two years?**

13. If the PR touches a flaky or quarantined test: is there an owner and an expiry, or is this the commit that deletes it? No retry-to-green. (10)

14. Is any coverage argument used as a signal rather than a target? (11)

15. For generated tests: seed logged outside the process, shrinking in place, minimized counterexample checked into the corpus? (5, 13)

16. For concurrency: is the claim "we explored interleavings with recorded schedules" rather than "we ran it a lot," with safety and liveness stated separately? (14)

17. For durability or recovery changes: which fault-matrix cells does this exercise, including stacked faults? (15)

18. For performance: distributions against a same-run baseline, confounders pinned or randomized, harness validated? (16)

19. Are tests being deleted? Which declared criterion fired, and where does the displaced risk now live? (18)


**Quarterly audit.** Quarantine list owned with no expired entries; XFAIL ledger reviewed for unexpected passes; mutation sample over the highest-value assertions with survivors triaged; coverage map read as archaeology; every trust-boundary parser has a live fuzz target and a minimized checked-in corpus; every durability and concurrency promise has a seeded test; fault matrices reviewed for empty cells; suite latency and flake rate inside budget; deletions each naming their criterion; trust metrics — re-run rate, time-to-fix, revert rate after green merges — reported to the engineers who stake releases on them.

## Contested territory, flagged honestly

A standard that pretends the contested questions are settled loses the senior engineers it needs to convince. Each flag gives this standard's position and the strongest argument against it.

**Mocks and interaction testing.** _Position_: real implementations by default, doubles only at owned boundaries, doubles verified by contract, interaction assertions only where the interaction crosses a contract boundary and _is_ the behaviour. The evidence is institutional — "at Google, we have found that this style of testing is difficult to scale" ([ch. 13](https://abseil.io/resources/swe-book/html/ch13.html)) — and Beck is blunter: too much mocking, especially strict mocking, is a structure-sensitivity nightmare ([Desirable Unit Tests](https://newsletter.kentbeck.com/p/desirable-unit-tests)). _Counterargument_: the London school treats mock-first as a _design_ discipline, not a verification one, and Fowler's taxonomy shows mockist testing is a coherent alternative verification style rather than a lazy shortcut ([Mocks Aren't Stubs](https://martinfowler.com/articles/mocksArentStubs.html)). The concession: mockist scaffolding is a defensible design technique during development and an indefensible permanent artifact, so it is replaced by boundary-level state tests before merge. Disagreements remain, and the rule is written to make them cheap to adjudicate — is the interaction observable at a contract boundary?

**Coverage numbers.** _Position_: signal always, target never; diff coverage as a review signal and at most a soft local gate; project-wide percentages never; kernel-level branch or MC/DC completeness only by explicit per-component decision. _Counterargument_, and it is honest: a floor, however gameable, protects against total test neglect on teams under deadline pressure, and Google itself publishes 60/75/90 tiers while endorsing near-100% per-commit goals ([Code Coverage Best Practices](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html)). The rebuttal is that a gameable floor buys that protection with vacuous tests, which are worse than absent ones because they are indistinguishable from real ones at a glance. A team that knows itself chronically under-tested may rationally adopt a floor _plus_ Rule 4's calibration, buying the protection without the vacuity.

**Always-red-first.** _Position_: red-first ordering is **not** mandated; "seen red for the right reason once" **is**. The best-controlled evidence is Fucci et al.'s replicated TDD experiments, which found that sequencing — test first or code first — "had no important influence" on quality or productivity, while granularity and uniformity of cycles did ([IEEE TSE 2016](https://arxiv.org/abs/1611.05994); [DOI](https://dl.acm.org/doi/10.1109/TSE.2016.2616877)). Mandating a design methodology on evidence supporting only a verification mechanism is legislating past the data. _Counterargument, and it is real_: canon TDD gets the calibration free and adds a design benefit no mutation run replicates — the API is consumed before it is built, so the test cannot be coupled to an implementation that does not yet exist ([Canon TDD](https://newsletter.kentbeck.com/p/canon-tdd); [Cooper](https://www.youtube.com/watch?v=EZ05e7EMOLM)) — and a relaxed rule is harder to audit and decays into ritual. The flanks: Fowler holds self-testing code can be produced test-after provided the work is not done until the tests pass ([Self-Testing Code](https://martinfowler.com/bliki/SelfTestingCode.html)), and DHH marks the far edge ([TDD is dead](https://dhh.dk/2014/tdd-is-dead-long-live-testing.html)). Prohibited either way is the third path: green-born assertions with no falsification evidence, ever. Bug fixes are the exception where ordering _is_ mandated, because there the red is the diagnosis.

**Test plans.** _Position_: heavyweight prose plans enumerating cases are forbidden; a one-page risk map plus a per-change test list is required, reviewed quarterly. _Counterargument_: the evidence that lightweight risk mapping survives contact with fast-moving teams is testimonial rather than measured, and the decay argument used against heavyweight plans applies at smaller scale too. The mitigation is the quarterly review, whose purpose is to make the rot observable rather than to prevent it.

**Pyramid ratios.** _Position_: ratios emerge from the risk map; none is mandated. The principle — small tests dominate because speed and determinism are the gate-compatible properties — is sound, and the numbers (70/20/10, 80/15/5) are folklore around it ([Just Say No to More End-to-End Tests](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html); [Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html); [SWE ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)). What the numbers must not excuse is a missing middle (the hourglass) or a missing top; the ceiling that does hold is one E2E test per critical journey ([What makes a good end-to-end test](https://testing.googleblog.com/2016/09/testing-on-toilet-what-makes-good-end.html)). _Counterargument_: a published ratio is a cheap auditable heuristic and a risk map is not, so ratio-free standards drift toward whatever the last incident produced. The concession: systems whose dominant risk _is_ integration — distributed systems, protocol implementations, storage engines — will rationally invert the pyramid toward simulation-level tests, and this standard permits the inversion when the risk document justifies it. That permission is defensible only because Rules 7 through 10 make the large tier deterministic enough to trust.

**Known failures.** _Position_: pinned XFAIL with owner, bug link, expiry, and inverted semantics — an unexpected pass is a failure. _Dissent worth recording_: one council view holds a known-failure test should encode the desired behaviour in a non-gating lane and never be normalized as success, on the grounds that inversion trains people to read red as fine. This standard adopts inversion because the browser engines have run it at scale for two decades and symmetry is what keeps the ledger honest — which is precisely why expiry and ownership are mandatory clauses rather than nice-to-haves.

## The standard, compressed

1. Test at the narrowest boundary that is a contract; if an internal needs testing, promote it to a module. _(Cooper; SWE ch. 12)_

2. Assert observable outcomes; harvest universals with a witness count, enumerate existentials; interactions only when the interaction crosses the boundary and is the behaviour. _(SWE ch. 12–13)_

3. One behaviour per test; every diff declares which of the four kinds of change it is, and only a behaviour change edits an existing expectation. _(SWE ch. 12)_

4. Every load-bearing assertion is shown able to fail and names its own check; diff-scoped continuous mutation where blast radius justifies it; never gate on a mutation score. _(SQLite; Petrović & Ivanković; Just et al.)_

5. Equivalence claims are proven by generated evidence — differential, property, metamorphic — with seeds logged outside the process, mandatory shrinking, counterexamples promoted, and correlated-oracle and bug-for-bug lock-in stated. _(SQLite SLT; QuickCheck; Wayne; TigerBeetle)_

6. Every assertion names its oracle; change detection is legitimate only when labeled, minimized, and reviewed. _(Barr et al.)_

7. Determinism is constructed at seams for time, randomness, scheduling, environment, identity. _(Fowler; Jepsen)_

8. Hermetic by default: owned scratch state, no ambient network, no shared mutable fixtures; share contracts, not scenes. _(SWE ch. 23; Luo et al.)_

9. Size classes with sandbox-enforced resource ceilings and suite latency budgets as SLOs. _(Google Test Sizes)_

10. Flakes leave the gate the same day with an owner and an expiry, are measured against a budget, and are never retried into silence. _(Google flakiness data; Fowler)_

11. Coverage maps what was not exercised — review signal, at most a soft local gate on changed lines, never a project target. _(Inozemtseva & Holmes; Google's coverage system; SQLite's MC/DC caveat)_

12. Every bug fix ships a test observed red on the unfixed code; irreproducible bugs get instrumentation and expanded exploration and stay open as suite deficiencies. _(SQLite policy; SWE ch. 12; Fowler)_

13. Fuzz what parses, property-test what transforms, keep the corpus as a permanent checked-in asset. _(OSS-Fuzz; dbsqlfuzz; AFL)_

14. Concurrency is tested by exploring interleavings with recorded schedules — four rungs from injected executors to full simulation — never by stress-and-pray. _(CHESS; TigerBeetle; Jepsen)_

15. Every durability or recovery promise is tested by seeded fault injection, including stacked faults, with the seed as the failure artifact. _(SQLite anomaly testing; Jepsen)_

16. Performance tests are controlled experiments: distributions, same-run baselines, validated harnesses, coordinated omission accounted for. _(Mytkowicz et al.; Tene)_

17. Golden artifacts are minimized, canonicalized, and re-baselined only through reviewed diffs; known failures are pinned XFAIL with inverted semantics. _(Dodds; WebKit/Chromium)_

18. Test code is production code — reviewed, named as behaviour, actionable on failure — and deletable only under recorded criteria. _(SWE ch. 11–12; Pryce)_

19. CI gates on hermetic suites, calibration evidence, contracts, and crash findings; never on coverage percentages, mutation scores, or anything retriable into green. _(Fowler; SWE ch. 23)_


And the meta-rule that generates them: a test suite is an instrument, and an instrument's three ways of lying — false confidence, false alarm, decay — are each preventable, detectable, and worth a rule that names them. A good test, in one sentence, is a deterministic, self-contained experiment that fails if and only if a stated promise is broken, and whose failure names the promise. The "if" is Rule 4; the "only if" is Rules 3, 7, and 8; the "stated promise" is Rules 1, 2, and 6; "names the promise" is Rule 18.

Do not count tests. Account for claims, counterexamples, and blind spots.
