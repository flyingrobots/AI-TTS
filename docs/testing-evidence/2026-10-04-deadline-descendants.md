# Deadline process-group cleanup

Change-kind: bug fix. Issue #105. Oracle: a timed-out command cannot leave a running member of its owned process group merely because the group leader exits first.

## Behavior and boundary

The deadline wrapper sends SIGTERM to its owned process group, retains the unreaped direct child as an identity anchor through the existing two-second grace period, then sends SIGKILL to remaining group members before reaping the child. A missing group at a signal boundary is benign. After a delivered SIGTERM, timeout cleanup consumes the full grace period even when SIGTERM already stopped the command. A group already confirmed to contain only zombies can finish immediately. This prevents a reused numeric group identifier from being mistaken for the original workload. Normal child exit propagation, timeout status 124, diagnostics and argument handling remain unchanged. Processes that deliberately create a different process group are outside this helper's ownership boundary; the validation watchdog separately stops the entire owned container.

The new medium regression enters through `main(argv)` with real subprocesses. Its Popen boundary wrapper waits for an owned child PID file, written after SIGTERM is ignored, before returning the real parent process to the runner. This establishes readiness before the actual deadline begins. The parent remains in the runner-created session and group, and exits on SIGTERM; its child remains in that group and ignores SIGTERM. A process-state query observes only the owned PID and fails closed on probe errors. A zombie counts as non-running. In the current fixture, `finally` signals and waits only while its direct child remains unreaped; it uses the same verified Darwin refusal handling as the production helper. Readiness checks do not reap the leader. The enclosing host watchdog stops the container after either RED or GREEN, retiring remaining fixture state. This is a process-liveness test, not a claim of descendant CPU attribution or a general-purpose process supervisor.

## Review correction: preserve process-group identity

The initial implementation and integration measurements above are historical coordinates. CodeRabbit approved the initial head but its supplementary architecture review identified an actionable identity-reuse race: `process.poll()` reaped the leader before the last group signal. If the original group disappeared and its identifier was reused, cleanup could target an unrelated group. The correction retains the leader until the final group signal, then waits for it. The former 50 ms polling loop is removed. The existing two-second grace is now always consumed on timeout; normal completion still returns immediately with the child's status.

The small `tests/test_deadline_identity.py` regression enters `main(argv)` with a controlled OS/process boundary that reuses the group identifier as soon as the leader is reaped. It observes signals delivered to the unrelated replacement, rather than asserting a private helper call sequence. Raw output and source hashes are retained as `identity-results.json` and `identity-inputs.json`. This controlled schedule is not a claim of reproducing PID reuse in the host kernel.

The same stopped reusable worker, validation lock, CPU/memory limits and storage/deadline watchdogs were used. The launch contract was refreshed before execution. The host guard records both successful command completion and successful whole-container termination in `identity-host-resources.json`. Apple's [XNU group-signal implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sig.c) filters zombie members and returns EPERM when it finds no signalable group member. The corrected wrapper retains the identity anchor and handles this Darwin result only after a fixed `/bin/ps` query confirms a nonempty owned group containing exclusively zombie states. Live members, missing confirmation, malformed output and probe failure remain errors. The process-state query has a one-second deadline; it runs only after a Darwin permission refusal. Unrelated groups are ignored, and the leader is never reaped to make the query succeed.

The six small controlled cases cover refusal at SIGTERM and SIGKILL for three membership states: owned zombies with an unrelated live process, an owned live member, and absent membership confirmation. On `ff0cda2`, both zombie-only cases fail and the four refusal cases pass. After correction, all ten focused deadline cases pass, including the real subprocess tests and identity-reuse schedule. Replacing the permission guard with unconditional acceptance fails all four refusal cases. These results, input hashes, clean Ruff/format/mypy output, and successful container termination are retained in the `darwin-*` artifacts. The process-table simulation is calibrated by the observed macOS failure; passing Linux simulations still require a fresh hosted macOS run.

## Review correction: fixture and replay teardown ownership
