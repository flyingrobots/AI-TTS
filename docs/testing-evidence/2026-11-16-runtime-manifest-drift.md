# Guided-runtime manifest drift repair

Date: 2026-11-16. Issue: [#172](https://github.com/flyingrobots/AI-TTS/issues/172).
Change class: bug fix. Author/reviewer: Codex.

## Failure and cause

Guided setup installs three checked-in requirement exports. The supply-chain
audit examined a fresh export of `uv.lock`, but did not compare the files that
setup consumed. Updating the lock left those installation inputs stale.

The new check uses uv 0.9.18, matching CI. It copies only `pyproject.toml` and
`uv.lock` to a temporary project, exports all three engine extras offline to
their canonical relative paths, adds the separately pinned English model to
both Kokoro exports, and compares exact bytes with the checkout.
Each export has a 30-second timeout. It downloads no model or package and fails
closed if export fails. Default check mode modifies no checkout file; explicit
`--write` regenerates the three installation manifests.

Before regeneration, the check exited 1 and named all three stale manifests.
After regeneration it exited 0. The frozen lock itself did not change.
Examples of corrected consumed pins are certifi 2026.10.19 in all three
manifests and Pillow 13.0.0 / Brotli 1.2.1 in Chatterbox.

## Falsification and preservation

For each manifest, separately replace the certifi version with the old version
and corrupt one SHA-256 hash digit. All six mutations were rejected with exit 1
and the changed manifest path. Each run left the mutated bytes untouched,
proving the check did not repair its input before comparing it. Restore the
original generated bytes after each experiment; the final check passes.

The generator retains the existing engine-extra mapping, platform/Python
markers, requirement hashes, and pinned Chatterbox/Perth source revisions.
It compares complete exports rather than a hand-maintained package subset.
Missing files or failed exports cannot count as an empty successful result.

The 36 affected model setup, CLI, daemon, managed-engine, and supply-chain
evidence tests passed locally. Ruff and mypy passed for the checker. Normal
hooks and current-head hosted CI remain required publication gates.

## Reproduction and boundary

Review found that the initial bare exports dropped the pre-existing English
language-model wheel from both Kokoro manifests. Two new tests enter through
`RuntimeInstaller.install` and inspect the exact requirements file passed to
pip. Both failed on the dropped dependency and pass with the original URL and
SHA-256 restored. The canonical `kokoro-supplement.txt` now makes this separate
pin explicit and part of both generation and comparison. It is not in the
lock's vulnerability graph. Removing it from a generated file is rejected by
the drift check.

Two CLI regressions also reproduced `FileNotFoundError` when the selected uv
was relative (`--uv ./tools/uv` or a relative `PATH` entry). Each test runs the
real checker with an owned executable exporter and temporary project. Resolving
the executable before changing the child working directory makes all three
exports run in both cases; both regressions now pass.
All four new regressions passed ten shuffled node-order runs in pairs (seeds
17201 through 17210): 40 passes. The 19-case combined setup/checker suite also
passed. These runs used CPython 3.14.7; the checker's real export used uv 0.9.18.

Use the commands in [Contributing](../../CONTRIBUTING.md#guided-model-runtime-requirements).
The CI supply-chain job runs the same check before its existing dependency,
source-revision, and license checks. No audit exceptions or resource limits
were changed.

This validates generated installation inputs and their consistency with the
audited lock. It does not prove every advisory applies to a live environment,
upgrade an installed runtime, or establish actual model synthesis/streaming.
No model weights were downloaded and no running daemon was restarted.
