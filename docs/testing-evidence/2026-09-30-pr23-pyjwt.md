## Contract, oracle, and red-to-green evidence

`tests/test_dependency_security.py` enters the dependency's public JWK/JWT
verification boundary. Its oracle is
[GHSA-9j54-fg26-wv3r](https://github.com/advisories/GHSA-9j54-fg26-wv3r):
an empty HMAC JWK must not authenticate a token signed with the known empty key.
The test is small: fixed bytes, a real local HMAC, no clock claims, network,
filesystem, subprocesses, or scheduling. It permits typed rejection either
when importing the empty JWK or when verifying, since both enforce the contract.
The test records its removal criteria beside the fixture.

On the parent's PyJWT 2.13.0, the regression reaches its assertion and fails
with `DID NOT RAISE InvalidKeyError`; the dependency accepts the token, emitting
only an insecure-key warning. With PyJWT 2.14.0 from the updated lockfile, the
same assertion passes: importing the empty JWK raises `InvalidKeyError`.
The final rejection boundary was exercised red on 2.13.0 and green on 2.14.0.
The vulnerable dependency is also the assertion's falsification witness.

Commands:

```sh
# Red, using the parent's dependency in the isolated worktree environment:
uv pip install --python .venv/bin/python pyjwt==2.13.0
.venv/bin/pytest tests/test_dependency_security.py
# Green, restore the updated frozen environment:
uv sync --frozen --group dev
uv run --frozen pytest tests/test_dependency_security.py
uv run --frozen pytest
```

The full suite passes: 559 tests, no warnings. Ruff check, Ruff format check,
mypy, and `uv lock --check` pass. The unchanged Swift code already passed all
97 tests with warnings-as-errors and hosted Xcode 26.3 CI at `774f00b`.

A local strict `pip-audit` of the hashed all-extras export reports no known
vulnerabilities after the update. Its local Python is 3.14, so the hosted
Python 3.12 all-extras audit remains the authoritative minimum-runtime check.
The local audit ignored malformed preexisting HTTP-cache entries and fetched
fresh results; those cache warnings are not test or compiler diagnostics.

This regression covers the empty-key advisory only; the strict audit checks
all reported advisories against the resolved graph. Neither is evidence that
AI-TTS's stdio transport exposes the vulnerable JWT verification path. Actual
application exploitability was not established and is not claimed.
